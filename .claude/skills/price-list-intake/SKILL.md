# Price List Intake

<!-- Restaurant skill. It reaches the restaurant's data ONLY through the
restaurant's own Bread 'n' Butter MCP (`.mcp.json` → /api/restaurants/<slug>/mcp,
verbs list_tables · list_rows · get_row · create_row · update_row ·
upsert_row · delete_row · write_rows · upload_vendor_file (alias
upload_invoice_file) · recipe_cost). It never holds a database address. The
column names are the restaurant database's (supabase/restaurant/0010 in the
app repo, spec "Vendor prices and the morning order" §Data contract); when a
migration renames one, update this file in the same change. `list_tables` is

A price list is what a vendor **says it will charge**. An invoice is what the
restaurant **paid**. The two never mix: a price list never becomes an invoice,
never prices an ingredient in `ingredient_costs`, and never moves a recipe
cost. Its only job is to let the kitchen compare vendors today — the database
view `ingredient_vendor_prices` sets every vendor's latest price beside every
other, in the ingredient's own unit, each with its source and age.

So the job is the same discipline as an invoice, with less at stake per line
and more lines: keep everything the paper says, invent nothing, and link each
line to the vendor product it is — by code, never by guesswork.

## What counts as a price list

| The document | `kind` |
|---|---|
| A distributor portal's order-guide export (US Foods, Sysco, a broadline's "my list" download) — the restaurant's usual items with today's case prices | `order_guide` |
| A purveyor's sheet of what it has and what it costs: a daily fresh sheet, a weekly market list, a catalogue page | `price_sheet` |
| A rep's answer to a price request, for named items, for a named day | `quote` |
| A machine feed from a distributor (EDI 832, a catalogue API) | `edi_catalog` |

**Not a price list:** an invoice, a delivery ticket, or an **order
confirmation** — those record a purchase and belong to invoice intake (an
order confirmation is `ordered`, never `received`: it proves only what was
asked for). A document that is neither, or that you cannot tell, is not
guessed at: park a `document_kind` decision on its reading ("What is this
document?") and write no price or invoice rows.

## Base Structure

Write by **column name**; you choose the uuids so the lines can name their
price list in the same batch.

```
ingredients ←── vendor_items ──→ vendors (rep, cutoff, delivery days, minimum)
                    ↑                ↑
            price_list_lines ──→ price_lists
            (one line, as printed)
```

### `price_lists` — one row per vendor document

| Column | Fill with |
|---|---|
| `vendor_id` | The vendor who will bill you at these prices. Find it with `list_rows` on `vendors` `{ "filter": { "name": … } }`; create one only when none exists |
| `kind` | `order_guide` · `price_sheet` · `quote` · `edi_catalog` (above) |
| `prices_as_of` | The day the prices apply to, from the paper ("Prices effective 10/28", "Quote for delivery Thu 10/29", the export's run date). Nothing printed → the day it was received, and say so in the report |
| `file_path` | The stored original: the payload's `file_path` when the app handed you a dropped file, or what `upload_vendor_file` answered (step 6). Never a URL you made |
| `summary` | One line: vendor, kind, how many lines, the date the prices apply to, anything odd ("82 lines, prices for Thu 10/29; 6 items marked out of stock") |
| `location_id` | Leave empty |

### `price_list_lines` — one row per line, as printed

| Column | Fill with |
|---|---|
| `price_list_id` | The price list's uuid |
| `vendor_item_id` | The vendor item matched by vendor + item code (Matching). **Empty when nothing matches** |
| `item_code` | The vendor's code, as printed, without `#`. Empty when the sheet prints none (common on a purveyor's fresh sheet) |
| `description` | The line text **verbatim**, wraps joined with a space |
| `brand` | As printed, title-cased; empty when none |
| `pack` | The pack **as printed** (`4/1 LB`, `115 CT`, `10# AVG`) — text, never broken down here |
| `unit_price` | The price per `unit`, as printed |
| `unit` | What `unit_price` is per: `CS` (the case) · `EA` (one inner pack, a split) · `LB` (a pound — catch-weight meat and fish, produce sold by the pound) |

A line offering both a case and a split price is **two lines**, one `CS` and
one `EA`, the same code on both. A line with no price ("market", "call", "out
of stock") is written with `unit_price` empty and the word in `description`
as printed — the sheet said it, so it stays — and it never links.

### `vendors` — ordering details

Read them, and fill a blank one only when the document prints it: the rep's
name and email on a quote (`rep_name`, `rep_email`), a cutoff ("Order by 2 pm
for next-day", → `order_cutoff` as printed), delivery days (`delivery_days`,
lower-case weekday names: `monday` … `sunday`), an order minimum
(`order_minimum`, dollars). A value already
set is the owner's: never overwrite it — a document that disagrees goes in
the report.

### `decisions` — what you park for the owner

| Column | Fill with |
|---|---|
| `price_list_id` · `price_list_line_id` | The price list and (for a line) the line it is about. Never `invoice_id` or `recipe_id` beside them — a decision belongs to one thing |
| `reading_id` | Only on a `document_kind` decision: the `invoice_readings` row of a document you could not classify (then no `price_list_id` — there is no price list) |
| `kind` | `new_product` (a vendor item to confirm) · `other` (a changed pack, anything else) · `document_kind` (what is this document?) |
| `title` | What is needed, in the owner's words |
| `notes` | The proposal, what it blocks and what clears it |
| `status` | `open` on create |

The app hands an answered decision with a `price_list_id` back to this skill,
and a `document_kind` one back to invoice intake (the reader), each as
`{ "decision_id": … }`. An `other` answered "Handled." is settled in the app
and never comes back.

## Procedure

0. **Open the door.** `list_tables` once: `price_lists`, `price_list_lines`
   and `ingredient_vendor_prices` are there. A refusal (401/403) means the
   token is wrong or read-only — stop and say so.
1. **Get the text out** with its layout kept (a PDF text extractor in layout
   mode; a spreadsheet read as its rows, header included). A photo is read
   directly; say the numbers were read from an image.
2. **Identify the vendor and the kind** (What counts as a price list). Open
   the vendor's reference file if there is one; no file → the general rules
   here, and write the reference as part of the job (header, columns, pack
   notation, traps). An invoice or order confirmation → stop and hand it to
   invoice intake. Unknown → park `document_kind` (with `reading_id` when
   there is one), stop.
3. **Refuse a duplicate.** `list_rows` on `price_lists` `{ vendor_id, kind,
   prices_as_of }`. One exists with the same number of lines and the same
   prices on the first and last lines → it is in; write nothing, say which,
   and stop. A second quote for the same day with different prices is not a
   duplicate — it is a revised quote, and the newer row wins in the view.
4. **List every line before writing anything**: code, description, brand,
   pack, price, unit. Count them against any printed count; a spreadsheet's
   row count is its count. A line you cannot read is listed as unreadable,
   never skipped and never filled in.
5. **Match** every line now (Matching), so the batch links the known ones.
6. **Keep the original.** No payload `file_path` → `upload_vendor_file`
   (`content_base64` up to 3 MB, or PUT the bytes to its `upload_url`) and use
   the `file_path` it answers. A refusal doesn't stop the price list: write it
   without `file_path` and say so.
7. **Write it in one batch.** One `write_rows`, in order: the vendor (only if
   none was found), the price list, every vendor item the owner approved,
   every line (linked or not), then any decisions parked. All or nothing.
   - **Refused** → nothing landed. Read the failing write's index, fix it,
     re-send the **whole** batch with the same uuids. Never line by line.
   - **No answer** → `get_row` on the price list's uuid says whether it
     landed; re-send only if it didn't.
   - **More than 200 writes** → the price list and its lines go in the first
     batch, the decisions after. A document of more than 199 lines can't land
     whole: stop and say so; never split a price list across two rows.
8. **Read it back** — `list_rows` on `price_list_lines` for this price list:
   the count, and the values of every line, match what you sent.
9. **Read the prices back** — `list_rows` on `ingredient_vendor_prices`
   filtered by each linked ingredient: a `price_list` row from this vendor
   whose `source_id` is this price list and `source_line_id` the line,
   `as_of` = `prices_as_of`, with a `price_per_unit`. A linked line that shows
   no price is a unit mismatch on its vendor item (`base_unit` ≠ the
   ingredient's unit) — say so; the vendor item is invoice intake's to fix.
10. **Check** (below), then **report**.

## Matching

**Vendor + item code** (`list_rows` on `vendor_items`, `{ vendor_id,
item_code }`), never description text. Found → link it. Then check the
**pack**: the printed pack must be the vendor item's pack
(`pack_count`/`pack_each_size`/`pack_each_unit`). Different → **do not link**:
the vendor changed the pack under the same code, and the view would price it
through the old conversion. Leave the line unlinked and park `other`
("Pack changed: Harbor HF-3317 now 2/5 LB, was 1/10 LB").

**No code on the sheet** (a purveyor's fresh sheet often prints none) → a
line may link only to a vendor item of **this vendor** whose description and
pack it unmistakably is, one candidate and no other; show it to the person
present, or (headless) leave it unlinked and list it in the report as a
likely match. Never link across vendors.

**No match** → the line stays **unlinked**, which is a complete outcome: it
is on file, it shows on the vendor's price list, it just isn't compared yet.
Most lines on an order guide are things this kitchen doesn't use; they stay
unlinked for good and that is correct.

**A new vendor item** — a line the kitchen does use (it is the same thing as
an existing ingredient, from a vendor that has no vendor item for it yet) —
is created **only with the owner's say-so**: shown to the person present as a
table (ingredient, code, pack, conversion), or parked headless as a
`new_product` decision with the proposal in invoice intake's fixed shape —
`EXISTING ingredient "<name>"`, `Conversion: 4 × 1 lb × 16 = 64 oz`, the case
rate. The conversion follows invoice intake's Conversions table and its
two-way check; a count↔weight crossing with no `each_weight_oz` is parked,
never guessed. The vendor item is created `verified` false.

**Never create an ingredient.** A price list says what a vendor sells, not
what the kitchen uses. A line for something with no ingredient stays
unlinked; if the owner wants it, they add the ingredient (recipe entry or
invoice intake does), and a later run links it.

## Rules

- **Prices as printed.** Never compute a case price from a split or a per-lb
  price, never convert, never round. The view does the pack-to-kitchen-unit
  math, the same math the costing uses, so a quoted price compares to a paid
  one as plain numbers.
- **Nothing here costs anything.** Never write `invoices` or
  `invoice_lines`, never touch an ingredient, a recipe or a recipe line. If
  the owner wants a quoted price to be what they paid, that is a purchase —
  it arrives as an invoice.
- **Never use the browser.** Prices come from documents the chef or a rep
  hands over; the `browser_*` tools are never used on a vendor portal, not
  even to download the export.
- **Blank beats guess** — a pack, a date, a brand the paper doesn't print is
  left empty and named in the report.

## Checks

| # | Check | Pass when |
|---|---|---|
| 1 | Count | lines written = lines on the document (or rows in the export) |
| 2 | Read-back | every line came back with the values sent |
| 3 | Pack | every linked line's printed pack = its vendor item's pack |
| 4 | Priced | every linked line has a `price_per_unit` in `ingredient_vendor_prices` |
| 5 | Move | a linked price more than **15%** from the same vendor item's last paid price (the view's `invoice` row) → flag: a slip in reading or a real move, both worth knowing |
| 6 | Untouched | `recipe_costs` for one dish that uses a linked ingredient reads the same before and after the write |

Report it as a table, ✓ or ⚠ per check with the numbers. A ⚠ is never
silent: what it blocks, what clears it.

**Report**: the checks, then the price list (vendor, kind, as-of, line count,
file), lines linked vs unlinked, each parked decision by title, every price
that moved more than 15% against what was paid, and — for each linked
ingredient — whether this vendor is now its cheapest fresh price
(`is_cheapest_fresh`).

## Resuming

When the owner answers a parked decision, the app runs this skill again with
`{ "decision_id": "<decisions.id>" }` — one decision at a time. The price list
is already in: do not create the price list or any line. Load
the decision (`get_row`), its price list (`price_list_id`), that price list's
lines, and every one of its decisions still `answered` (finish them all in
this run — each is applied once). A decision that is not `answered`, or has
no `price_list_id`, is not this skill's: report it and stop. Apply each answer once — `Approved as
proposed.` creates the vendor item from the proposal (conversion re-checked
two ways) and links the line, in one `write_rows` with the decision set
`done`; `Edit before adding: <note>` applies the note, or sets the decision
back to `open` quoting it when the note doesn't settle the conversion
(when an answer turns on what the document printed — a pack, a brand, a line
the note points at — read the original with `get_vendor_file
{ price_list_id }`, a 15-minute link; never guess it from the stored line);
`Handled.` is only the row. Then re-run the checks over the whole price list
and report what was applied and what is still parked. A resume never asks
anyone.

## Running headless

The app's single upload drop stores the file, writes an `invoice_readings`
row and dispatches the restaurant repo's "Run a skill" job with invoice
intake — the reader — and `{ file_url, file_path, reading_id }`. The reader
works out what the document is; a price document carries on as this skill in
the same run, with the same file and `reading_id` — also when the owner
answered "what is this document?" and the reader fetched the stored file back
with `get_vendor_file { reading_id }`. The job's "Run workflow"
can also name this skill directly with the same payload. Every gate is
park-and-notify, a duplicate is refused, and the run ends with
`job/report.md` and `job/outcome.json` carrying the reading's `kind`
(`order_guide` · `price_sheet` · `quote`) and `price_list_id`; the job closes
the hand-off row (`status`, `kind`, `price_list_id`, `summary`) itself — never
write it.
