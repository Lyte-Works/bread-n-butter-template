# Presence Report

<!-- Restaurant skill. It reaches the restaurant's data ONLY through the
restaurant's own Bread 'n' Butter MCP (`.mcp.json`; verbs list_tables ·
list_rows · get_row · create_row · update_row · upsert_row · delete_row ·
write_rows, plus one `<alias>__request`
tool per connection the restaurant has added). Column names are the
restaurant database's (supabase/restaurant/0006_presence.sql); when a
migration changes one, update the tables here in the same change. How the
screen reads the rows is the app repo's src/src/lib/presence.ts. -->

A presence report answers one question for an owner who is not a marketer:
*are more of the right people finding us than last week, and what is the one
thing to fix?* The job is to read what each platform already knows, say each
number in a sentence a cook would understand, say what moved, and name at most
three fixes. A short true report beats a full invented one.

**Nothing is invented and nothing is guessed.** Every number is read from a
platform through a connection. A platform with no connection is skipped and
named in the summary — never estimated, never carried over from last week as
if it were new.

## Base Structure

Four tables, written by **column name**; `id` is generated and every write
answers with the stored row.

**A row is found by what it is, not by its id.** Each table has a natural
key for one run — the report by `run_date`; a number by `run_date` +
`surface` + `metric_label`; a search by `run_date` + `query` — and every
write of them is an **upsert** on that key: the one row that matches is
updated, none → it is created. That is what makes a re-run of the same week
change rows in place instead of adding to them. An upsert refused because
**more than one row matches** means an earlier run left a duplicate: list the
rows of that key, keep the newest, `delete_row` the others (same run_date
only), and send the upsert again.

### `presence_reports` — one row per run_date

| Column | Fill with |
|---|---|
| `run_date` | The Monday the week starts or the day the job runs — one date per run, `YYYY-MM-DD` (a re-run reuses it) |
| `headline` | One sentence, plain, about the single biggest thing that moved. Not a score, not a metric name |
| `summary` | What changed, **a paragraph per line** (lines are separated by a newline). Last line names any skipped platform: "Not checked this week: Bing (not connected)." |
| `top_fixes` | At most 3, numbered: `1. Do this. Because. 2. Then that.` Each starts with an imperative, then why in one sentence |
| `status` | `draft` while writing, `final` when every row below is written. The screen shows the latest `final` |

### `presence_snapshots` — one row per number per surface

| Column | Fill with |
|---|---|
| `run_date` | Same as the report |
| `surface` | `search_console` · `bing` · `google_business` · `maps` · `ga4` · `pagespeed` · `ai_answers` · `social` |
| `metric_label` | What the number counts, in the owner's words ("Calls from your listing") |
| `metric_value` | The number (a plain numeric; seconds as seconds) |
| `delta` | Movement vs the previous report, ≤ 24 characters: `+12%`, `−3`, `−0.1`; `first reading` when there is nothing to compare |
| `summary` | **The number in one plain sentence** — what it counts and what it means for the restaurant. Never empty |
| `sort_order` | Position within its surface, most important first (0, 1, 2…) |
| `details` | Only what is needed to explain the number: the date range, the page or query it came from, the endpoint. Never a raw API answer |

### `presence_searches` — what people searched

`run_date`, `query` (as the platform reports it), `count` (times you showed up for
it), `summary` (a note only when it says something: "You don't serve brunch;
these people leave." — otherwise empty). Keep the top 10.

### `presence_alerts` — what needs the owner now

`title` (what is wrong, in a few words), `summary` (what to do, in a sentence),
`severity` (`low` · `normal` · `high` · `urgent`), `status` (`open` →
`resolved` or `dismissed`). Alerts have no run_date: they stay open until the
cause is gone.

## What each surface covers

| Surface | Reads | Connection it needs | Typical numbers |
|---|---|---|---|
| `search_console` | Google Search Console | Google | Searches that showed you; clicks to your site; top queries (→ `presence_searches`) |
| `bing` | Bing Webmaster Tools | Bing | Searches that showed you on Bing; clicks |
| `google_business` | Google Business Profile | Google | Calls from your listing; direction requests; website clicks; new reviews |
| `maps` | Maps listing and rating | Google | Rating; review count; whether hours, phone and address match the restaurant's own |
| `ga4` | Google Analytics | Google | Visits to your site; where they came from; the page they open first |
| `pagespeed` | PageSpeed on the menu page | none (public) or Google | Menu page load on a phone, in seconds |
| `ai_answers` | Ask AI assistants about the restaurant | the AI connection | AI answers that named you, out of those asked |
| `social` | Buffer | Buffer | Posts sent; reach or engagement the account reports |

## Procedure

1. **Find what you can read.** `list_tables` to confirm the four Presence
   tables exist (if not, stop: the restaurant's database lacks migration
   0006 — say so). List the connection tools your MCP offers (`<alias>__request`).
   Map each surface to a connection; a surface with none is **skipped**, and
   you keep its name for the summary. Say the plan out loud before reading:
   surfaces read, surfaces skipped.
2. **Fix the run_date** (the date given, else today's) and the **window**: the
   last seven full days, and the seven before them for any platform that
   cannot hand you last week's number itself. Write both dates into `details`.
3. **Open this week's report.** `upsert_row` on `presence_reports`, `match`
   `{ run_date }`, `values` `{ status: "draft", headline: <placeholder> }`.
   The answer's `created` says which: `false` → this is a re-run of the week
   (its rows below are updated, not added to); `true` → the first run. Either
   way every row below has a home and a half-finished run never shows as
   final.
4. **Find last week's numbers.** `list_rows` on `presence_reports`, sort
   `-run_date`, the newest whose `run_date` is **before** this one; then
   `list_rows` on `presence_snapshots` for that `run_date`. These are the only
   source of `delta` — never recompute last week from the platform when a
   stored row exists. No earlier report → every delta is `first reading`.
5. **Read each connected surface**, one request at a time, narrowed by the API's
   own date and row limits, taking only the numbers named above. A request that
   fails, is refused (`{ status: "parked" }` means a person must approve — park
   it, do not retry), or returns nothing usable makes that surface *skipped*,
   named in the summary with the reason in three words. Never fill the gap.
6. **Write each number.** Compute `delta` from step 4's row of the same
   `surface` + `metric_label`: percent (rounded to a whole number) for counts,
   absolute (one decimal) for ratings and seconds. Then write the sentence
   (below). Every reading is an upsert on `presence_snapshots`, `match`
   `{ run_date, surface, metric_label }`, `values` the rest — sent together
   as one `write_rows` of `upsert` writes, so the week's numbers land
   together. A refusal names the failing write's index: fix that one and
   re-send the batch.
7. **Write the searches.** The top 10 the same way: one upsert each on
   `presence_searches`, `match` `{ run_date, query }`, in the same batch as
   the numbers or one of their own.
7b. **Clear what is stale for this run_date.** A re-run can leave rows an
   earlier run of the same date wrote that this run did not: a number whose
   surface was skipped this time or whose label is no longer read, a query
   that fell out of the top 10. `list_rows` on `presence_snapshots` and
   `presence_searches` for the run_date; every row this run did not just
   upsert → `delete_row` it (as `delete` writes in one `write_rows`, or one
   by one). **Only this run_date** — an earlier week's rows are the history
   every delta is read from, and are never touched.
8. **Write the alerts.** `list_rows` on `presence_alerts` filtered `status`
   `open`. For each problem found (below) with an open alert of the same
   `title`: `update_row` it; none: `create_row`. An open alert whose cause is
   gone (the hours now match, the listing is verified) → `update_row`
   `status` `resolved`, `resolved_at` now. Never reopen a `dismissed` alert for
   the same title; the owner decided.
9. **Write the report.** Compose `headline`, `summary`, `top_fixes` (rules below),
   then `update_row` the report (its `id` from step 3's answer) with `status`
   `final`.
10. **Verify**, every run: `list_rows` on `presence_snapshots` for the
    run_date — every row has a non-empty `summary`; no `surface` + `metric_label`
    appears twice; every skipped surface has no rows this run_date; the report
    is `final`; at most three numbered fixes. Fix what fails, then reply.

## Judgement rules

**Every number gets a sentence.** The screen prints `summary` under the number
and nothing else; a bare number is a failure. The sentence says what the
number counts and what it means, in kitchen words: "People who tapped Call on
Google", not "GBP phone-call actions". Avoid acronyms (impressions → "times
you showed up", CTR → "share who clicked", GA4 → "visits"). If you can only
describe it with jargon, you do not understand it yet — read it again or
leave it out.

**The headline names one thing.** Pick the movement the owner would most want
told over the phone: the biggest change that is also one they can act on. Flat
week → say it is flat ("A steady week…"), never manufacture news.

**Delta is honest about small samples.** A swing on a base under about 20
(2 calls to 3) is a +50% that means nothing: write the absolute change (`+1`)
and say in the sentence that it is a small number. Never round a fall into
"steady".

**Top fixes are things the owner can do this week**, ordered by what costs the
most if left, at most three. Each is a verb, a place and a reason: "Fix your
Sunday hours on Google. It says you close at 9; you close at 10." A fix
needs evidence in this week's rows or a platform answer — "post more" with no
number behind it is not a fix. If nothing needs fixing, write one fix saying
to keep going and name what is working, or leave `top_fixes` empty.

**What becomes an alert.** Only things wrong *now* that cost the restaurant
guests: wrong or missing hours, phone or address on the listing; the site or
menu page failing to load; a verification, suspension or sign-in problem on
a platform; a sudden collapse (more than half) in a core number with no
seasonal reason. A slow week is not an alert. `urgent` = guests are being
turned away today; `high` = wrong information is live; `normal` = fix soon;
`low` = tidy.

**Never compare unlike things.** A different window, a different page, a
different query set. If the platform changed what it reports, `first reading`
beats a false delta.

**Skipped is a finding, not a failure.** "Not checked this week: Bing (not
connected)" is the right ending of the summary, and it tells the owner what
connecting one more service would add.

## How it's scheduled

This skill is run, not scheduled by itself. The restaurant's repo (from the
template) must run it weekly: a scheduled workflow that dispatches the
"Run a skill" job with `presence-report` once a week (Monday morning, in the
restaurant's time zone — so `run_date` is that Monday), using the restaurant's
own MCP token, with nothing else in the prompt. The job must run it **again
safely**: a retry or a manual "Run now" in the same week upserts that
week's rows on their keys (steps 3, 6–7) and deletes what the earlier run
of the same date wrote and this one didn't (7b), so the week ends with
exactly this run's rows — never more, never stale ones looking current. It is a lane with no
person present, so any `{ status: "parked" }` answer ends that surface for the
week instead of waiting.

## Verification

- The report for the run_date is `final` and the only one for that date.
- Every snapshot has a plain `summary`, a `delta` and a `sort_order`; no
  duplicate `surface` + `metric_label` for the run_date.
- Every `delta` traces to a stored row of the previous report, or reads
  `first reading`.
- `top_fixes` has at most three numbered items, each backed by a row or an alert.
- Every surface with no connection is named in the summary and has no rows.
- Re-running the same run_date changed rows in place: no `surface` +
  `metric_label` or `query` twice for that date, and every row for that date
  is one this run wrote (anything else was deleted in 7b).
